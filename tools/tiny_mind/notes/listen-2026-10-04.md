# Listening: how much voice data? (2026-10-04)

Question: does the 52k-line set beat smaller sets, or is volume past the point of paying? Run in the cloud VM
(2 cores, ~1.4 s per voice step), scratch copy of `voice.py`'s format and loss (reply-only loss + 0.3 × SODA replay),
same base (`models/hybrid19-base-bf16.pt`), same seed, **one fixed held-out set of 2,000 lines** that no run
trains on, nested train subsets. Tool score: generate a reply for 60 held-out `become` rows, count the ones that
carry exactly the right tool. All numbers below are **measured**.

## What it says
- **The new lines fix the tools.** Every run trained on the new data reaches 43–48/60 on held-out become
  requests, against 8/60 for the shipped voice. That was the plan's top goal (35% → 18/20 target).
- **At this budget, data size doesn't separate the runs.** All three bottom out at ~2.5 around step 300 and
  then *rise*, including the full-data run at only 0.38 epoch, where overfitting is impossible. **Inference:**
  the rise is the recipe, not the data: `voice.py` holds a constant learning rate (Muon 0.005, AdamW 1e-3)
  with no decay, and after ~300–600 steps it starts to drift. `voice.py` hid this on 1.2k lines because it keeps
  the best epoch out of six short ones. The 43 vs 48 tool spread is within what 60 samples can tell apart.
- **So: is 52k too much?** Not shown. With a constant LR none of the runs gets to use more than ~10k examples
  before drifting, so the extra data never gets a fair chance. The fair test is the same curve with a decaying
  learning rate (warmup, then linear decay to 0 over the run).
